# Contributing

This file covers what you need to send a change. The [README](./README.md) explains the stack and the local dev environment, and [ARCHITECTURE.md](./ARCHITECTURE.md) explains where code lives.

## Setup

Install [Bun](https://bun.sh/docs/installation), then install dependencies in each of the three packages:

```bash
bun install
(cd app && bun install)
(cd app/agent && bun install)
(cd native && bun install)
```

Skipping one gives errors such as "Cannot find package 'zod'".

## Run the app

`just dev` starts the local stack with Podman and Tailscale. The README has the prerequisites, the admin email setting and how to reach the app from a phone. See [Development](./README.md#development).

## Run the tests

```bash
bun run test
```

Run this from the repo root. It runs each test file in its own process. A plain `bun test` over `app/` shares SQLite, ports and modules between files and reports hundreds of false failures. The root command stops at the first failing file.

To run one file while you work:

```bash
cd app && bun test test/<file>.test.ts
```

Tests that need Ergo, Podman or a coding agent skip themselves unless an environment variable turns them on. You do not need those to send a change.

CI also runs a typecheck. Run it with `cd app && bun run typecheck:ci`. It fails on errors that are not in `app/typecheck-baseline.txt`, so new code must not add any.

Scripts that import `app/src` open `/data/chat.sqlite` by default. Set `DB_PATH=/tmp/x.sqlite` when you run one outside the container.

## Where code goes

[ARCHITECTURE.md](./ARCHITECTURE.md#where-new-code-goes) lists where a new route, client feature, partial or stylesheet belongs. In short:

- Server routes in `app/src/routes/`, rules in `app/src/`, shared HTTP helpers in `app/src/http/`.
- Client features in `app/client/features/`, shared client parts in `app/client/core/`, markup in `app/partials/`, styles in `app/styles/`.
- Code the app and the `slirc-agent` package both use in `app/shared/`.

A size test (`app/test/size-guards.test.ts`) fails when a source file passes its line limit. If yours does, split the file along the lines above. Raise a limit only with a reason in the PR.

## Generated files

Some files are built from others and committed. Edit the source, run the command and commit both.

- **Partials are the markup source.** `app/public/index.html` is generated. Edit `app/partials/*.html`, then run `bun run assemble` in `app/`. A test fails if the committed `index.html` does not match the partials.
- **Styles** are `app/styles/*.css`. `app/public/style.css` is generated by the same `bun run assemble`.
- **Docs** are `app/docs/*.md`. Run `bun run docs` in `app/` to rebuild `app/public/docs/`. Do not hand-merge generated docs. Rerun the command.
- **The agent package** is `app/agent/src`. Run `bun run build` in `app/agent` and commit `app/agent/dist`.

If you change behavior a guide describes, update the guide too. The help bot answers from those docs.

## Commits

Write one short sentence in the imperative that says what the change does, with no prefix and no trailing period. For example, "Fold the workspace rail to the current workspace". Add a body when the reason is not obvious. Keep each commit to one change that leaves the tests passing.

## Pull requests

Open pull requests against `main` on [bitbonsai/slirc](https://github.com/bitbonsai/slirc). Fork the repo and push a branch to your fork. Only the maintainer pushes to `main` directly.

- Keep the pull request to one change. Say what changed and why, and how you checked it.
- Run `bun run test` and the typecheck first. CI runs both on every pull request.
- Add a focused test for new logic. If you changed the UI, say which browsers or devices you looked at.
- Never commit secrets, `.env` files or runtime data.

Report security problems privately, as [SECURITY.md](./SECURITY.md) describes. Do not open a public issue for them.
